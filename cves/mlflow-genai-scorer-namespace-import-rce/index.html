Remote code execution in MLflow third-party scorers

MLflow's third-party scorer deserialization can import caller-placed modules and execute Python code on affected tracking servers.

Summary

MLflow’s third-party scorer deserialization imports a Python module and instantiates a class selected by the request. A caller can chain experiment creation, run creation, and artifact upload so that the uploaded module lands beneath an allowed scorer package, then trigger its import through the scorer invocation endpoint.

The import runs in the tracking-server process. In the default no-auth configuration, the public advisory rates this as critical. The proof below is limited to a harmless marker write in an isolated test instance.

Affected versions and severity

Affected versions are >= 3.12.0rc0 and < 3.17.0. MLflow 3.17.0 contains the fix. The advisory assigns CVE-2026-116692 and rates it CVSS v3.1 9.8 Critical.

Research and acknowledgement

The official advisory credits Carlos Munhos (mskca) as the reporter. This research used multiple frontier AI models together as part of the vulnerability-hunting process. Thank you to the MLflow maintainers for coordinating the disclosure and remediation.

Technical details

Request-controlled module selection

MLflow 3.12.0 introduced third-party scorer registration in OSS MLflow. During deserialization, the server accepts module names equal to or beneath one of four scorer package roots: ragas, deepeval, trulens, and phoenix. It imports the selected module, resolves the selected class, and constructs it before validating the resulting scorer object. A package-name prefix check does not establish that the imported code came from the installed package.

The vulnerable sequence is a string-prefix check followed by import, class lookup, and construction:

allowed = module_path == root or module_path.startswith(root + ".")
module = importlib.import_module(module_path)
scorer_class = getattr(module, class_name, None)
scorer_instance = scorer_class(**init_kwargs)

Because the request controls module_path and the server can write beneath the package root, a newly uploaded descendant module can satisfy the check. The related source files are linked below.

Artifact placement and import path

Experiment creation accepts a file-backed artifact_location. A run created under that experiment receives an artifact directory below the selected location, and the artifact upload endpoint writes the supplied module there. If that location is beneath a writable allowed scorer package, Python can import the run and artifacts directories as namespace packages. The run ID returned to the caller supplies the corresponding module path.

The scorer invocation handler deserializes and constructs the scorer before it resolves trace IDs. The import is synchronous and does not depend on background job execution. A later HTTP 500 can therefore occur after the uploaded class has already run; the marker is the proof, not the error response.

Preconditions and authorization

  • The experiment, run, artifact-upload, and scorer-invocation routes must be reachable.
  • The MLflow process must be able to write beneath an allowed scorer package.
  • With authentication disabled, the default configuration requires no credentials. With basic authentication enabled, the caller still needs permissions to create an experiment and run and upload artifacts; the advisory notes that scorer deserialization itself is not gated by an experiment-specific permission check before import.
  • The code runs with the privileges of the MLflow server process. The official v3.14.0 image used in the advisory runs as uid 0; that does not by itself establish host-level access outside the container.

Reproduction steps

Use only a disposable MLflow v3.14.0 instance that you own. Bind it to loopback, disable container egress, mount no host secrets or sensitive directories, and remove the instance after the check. The proof writes one fixed marker beside the uploaded artifact; it does not execute a shell command or make a callback.

  1. Start the official v3.14.0 image in the isolated environment and confirm that the MLflow process can write to the selected allowed scorer package directory.

  2. Create an experiment whose file-backed artifact location is that package directory, then create a run and record its returned run ID.

  3. Upload the marker-only module shown in the proof-of-concept section as marker_probe.py in the run’s artifact directory.

  4. Submit the scorer object shown below to POST /ajax-api/3.0/mlflow/scorer/invoke. The endpoint expects this object JSON-encoded in its serialized_scorer field; replace <run_id> with the ID from step 2.

  5. Retrieve execution-proof.txt through the same run’s artifact-download endpoint and verify that its contents exactly match MLFLOW_MARKER_ONLY. The minimal class is not a complete scorer, so a later HTTP 500 is possible after the constructor runs.

  6. Tear down the isolated test instance and delete the artifacts created for this check.

Proof of concept

This is the harmless module uploaded in step 3. It creates a fixed text marker beside itself and performs no other action:

from pathlib import Path


class MarkerOnly:
    def __init__(self, **kwargs):
        Path(__file__).with_name("execution-proof.txt").write_text(
            "MLFLOW_MARKER_ONLY\n",
            encoding="utf-8",
        )

The scorer data in step 4 points to that file and class. The request sends this scorer object JSON-encoded in serialized_scorer:

{
  "name": "marker_only",
  "third_party_scorer_data": {
    "module": "mlflow.genai.scorers.trulens.<run_id>.artifacts.marker_probe",
    "class": "MarkerOnly",
    "metric_name": "marker_only",
    "kwargs": {}
  }
}

Replace <run_id> with the ID returned when the run was created. A matching artifact proves the constructor ran; an HTTP 500 by itself does not.

Impact and remediation

Successful exploitation provides Python execution with the privileges of the MLflow server process. The reachable data and systems depend on the process account, authentication configuration, filesystem permissions, and container isolation.

Upgrade to MLflow 3.17.0 or later. The safer design is to map scorer types to exact server-owned classes and validate class provenance before importing or constructing them. Keep installed application packages read-only to the service account, and constrain local artifact roots to a service-owned data directory.
